Part A · Orientation

1. How to use this guide

Think of this as a course, not a recipe. Part B explains how each piece of the app should work and why. Part C walks you through building it in stages, and each stage points back to the design notes it relies on.

Every stage follows the same pattern:

You'll learnThe new concepts and skills this stage introduces.
StepsWhat to build, in a sensible order.
Think aboutDecisions you need to make, and the trade-offs.
Watch outCommon mistakes that cost beginners the most time.
Check yourselfQuestions you should be able to answer before moving on.
Done whenA testable finish line, so you know the stage really works.

Habits that will save you

  • One new thing at a time. If you add a new library, a new table and a new screen at once and something breaks, you won't know which caused it.
  • Commit to Git every time something works. A commit is a save point you can return to.
  • Keep a decisions log. Keep a simple text file in the project noting what you decided and why. Future-you will forget.
  • Understand before you paste. When an AI assistant or tutorial gives you code, ask it to explain each part until you could rewrite it yourself. Code you don't understand is code you can't fix.
  • Test on a real phone early. Artists will use this at markets, mostly on phones. A laptop browser hides many problems.

2. What we're building

An app that helps an artist answer three questions at any time: What did I spend? What did I earn? Did it make money? It can be broken down by event, financial year and income stream.

Core (first release)Private accounts for artists in any country · onboarding with country, time zone, home currency and sales-tax setting · expenses with receipt photos · income across seven income streams, including cash sales · foreign-currency amounts converted and locked · events and venues (including vendor shelves) · reports by financial year, event and stream · CSV and FY summary exports · CSV import.
Assisted entryAutomatic reading of receipt photos into a draft expense, which the artist checks before saving.
Later additionsForward-to-email receipt inbox · Square and Stripe connections to pull sales automatically · optional offline queue for market days · helper logins with permissions chosen by the artist (the database is ready for this from day one).
Not the app's jobDeciding what is tax-deductible, lodging tax, BAS or VAT returns, or giving tax advice in any country. The app records and organises; the artist and their accountant decide.

Part B · Design notes

5. Accounts, team-ready access and privacy

People and businesses are different things

The database separates two ideas:

  • A user is a person with a login (an email address and one-time codes).
  • An account is an artist's business: its records, settings and receipts.

An account member row connects the two. It says which users belong to which account and what each may do. Today every account has exactly one member: the artist, as owner. Because every rule already goes through membership, adding a helper later means adding a row, not redesigning the database.

What the artist sees None of this. When someone signs up, a database trigger creates their account and makes them its owner automatically. There's no "create a business" step; the app simply feels like their own private account.

How the privacy rule works

Every business record carries an account_id, the business it belongs to, and a created_by, the person who entered it. The second one is useful for history now and for helpers later. The database checks every request: you can only read or change rows of an account you're a member of, and only in ways your permissions allow. This is called Row Level Security (RLS).

Why in the database and not just the screens? Anyone can open browser tools and send requests directly to your database address. If the only protection is "the screen doesn't show it", the data isn't protected. RLS means even a hand-crafted request gets nothing.

-- One function answers: "may the current user do this, in this account?"
create schema if not exists private;

create function private.has_permission(target_account uuid, needed text)
returns boolean
language sql stable security definer
set search_path = ''
as $$
  select exists (
    select 1 from public.account_members m
    where m.account_id = target_account
      and m.user_id = (select auth.uid())
      and m.status = 'active'
      and (m.role = 'owner' or needed = any (m.permissions))
  );
$$;

grant usage on schema private to authenticated;

-- Every business table uses it in its policies
alter table public.expenses enable row level security;

create policy "Members with permission can read" on public.expenses
  for select to authenticated
  using ( private.has_permission(account_id, 'transactions.view') );

create policy "Members with permission can add" on public.expenses
  for insert to authenticated
  with check (
    private.has_permission(account_id, 'transactions.add')
    and created_by = (select auth.uid())
  );

-- Repeat for update and delete, each with its own permission.
What "security definer" means here The function runs with its creator's rights, so it can read the membership table even though that table has its own RLS. That avoids a policy that has to check itself in a loop. Two safety habits come with it: keep such functions in a schema the browser can't call directly (here, private), and always set search_path. This function is the most important lock in the app, so ask for it to be reviewed specifically.

The permission list: define it now, use it later

PermissionAllows
transactions.viewSee income and expenses
transactions.addAdd income, cash sales and expenses, and upload receipts
transactions.editEdit or delete entries. Consider an "own entries only" version for helpers.
reports.viewSee reports and profit
exports.downloadDownload CSV exports

Owners have every permission. A helper running a market stall might only get transactions.add: they can log sales and upload receipts, but can't see profit.

Rules that keep the team model safe

  • An account always has at least one owner. The last owner can't be removed or downgraded.
  • Nobody can change their own role or permissions. Member changes go through a server route that checks members.manage.
  • Removing a member takes effect immediately, because RLS checks membership on every request.
  • Receipt files follow the same rule: storage paths start with the account_id, and storage policies call the same permission function.
  • Billing and deleting the account are owner-only actions.

Whose settings are they?

Belongs to the account (shared by everyone in it)Belongs to the person
Country, time zone, home currency, financial-year start, sales-tax settings, income streams, categories, events and venuesDisplay name, preferred language and number format
Why build this now if helpers may never happen? It costs one extra table, one function and slightly longer policies. Adding it after launch would mean changing every table, policy, storage path and query while real customer data is live. Building it in now is cheap insurance.

Logging in with a code, not a link

On iPhones, an app added to the Home Screen keeps its own separate cookies and storage from Safari. Login links and password-reset links in emails open in Safari, so the user ends up logged in to Safari, not the installed app. A 6-digit code avoids that: the user reads the code from their email and types it into whichever app they're in.

  • Use Supabase's email OTP sign-in. It handles both new and returning users.
  • Set up a custom SMTP email provider before anyone other than you signs up. Supabase's built-in sender only delivers to your own team's addresses, at roughly two messages an hour.
  • "Sign in with Google" or passkeys can come later. Test them inside the installed iPhone app before offering them.

Other account essentials

  • Settings: account settings for those with settings.manage; personal settings for everyone.
  • Delete account: owner only. Removes data and files, with a clear warning that tax records must be kept for years (5 in Australia; other countries set their own periods).
  • Download my data: your CSV exports cover this.
  • Secrets: the Supabase "publishable" key is safe in the browser only because RLS protects every table. The "secret" or service-role key and all AI, email and exchange-rate keys stay on the server.

6. Countries, time zones and financial years

Artists from any country can sign up at launch. The aim for every date decision is accurate first, with the least possible effort for the artist. In practice that means good defaults the artist only has to confirm.

The key idea: store a date, not a moment A receipt says "1 July 2026". That's a calendar date, not a moment in time. Store it in a date column exactly as written, and it can never shift. If you store it as a timestamp, it gets converted to UTC. 9am on 1 July in Melbourne is still 30 June in UTC, so the receipt drops into the wrong financial year. Storing calendar dates removes most time-zone risk before you write any time-zone code.

Where time zones are actually needed

  1. The default date on new entries. Use the date on the artist's device right now. At an interstate or overseas event, the receipt in their hand is dated in local time, and so is their phone. It's always editable.
  2. Timestamps from outside systems (Square, Stripe, CSV files with times) are turned into calendar dates. Use the account's time zone, or the event's time zone when the sale belongs to an event held somewhere else.
  3. Server jobs and history views, such as "created at" times, and knowing when "today" is for scheduled tasks.

Events and venues therefore get an optional time zone, defaulting to the account's. A Melbourne artist selling at a convention in Los Angeles then gets correct dates on that weekend's imported card sales.

The onboarding flow

  1. Country: pre-selected from the browser's language and region (e.g. en-NZ → New Zealand). Everything below is defaulted from it.
  2. Time zone: auto-detected and shown for confirmation. For countries with several zones (Australia, the US, Canada), the dropdown lists only that country's zones, using a small country-to-zone list from the IANA time zone database. 
    // Runs in the browser
const detected = Intl.DateTimeFormat().resolvedOptions().timeZone;
// e.g. "Australia/Melbourne"
  3. Home currency: defaulted from the country (Australia → AUD) and confirmed (§9).
  4. Sales tax: the right question for the country, e.g. "Are you registered for GST?" or "Are you VAT-registered?" (§8).
  5. Financial year: pre-filled from the country, editable.
  6. Income streams: the seven defaults, already ticked, editable later (§10).

These are saved on the account (§5). Nobody gets into the app until onboarding is complete, but each step is a single tap when the defaults are right.

Financial-year defaults

CountryDefault yearNote

These are starting defaults for individuals and sole traders. Some businesses use a different year, so the setting stays editable. Store both the start month and the start day. A few tax years start mid-month (the UK's starts on 6 April), and supporting that now costs nothing.

Showing dates and amounts the local way

  • Store one way, show the local way. Always store 2026-07-01. Display it in the person's format: 1/7/2026 in Australia, 7/1/2026 in the US, 01/07/2026 in Malaysia. JavaScript's Intl.DateTimeFormat does this for you.
  • Use the phone's own date picker instead of a typed date. It's faster and removes the 3/4 versus 4/3 confusion entirely.
  • Accept the local decimal mark. Many countries type 12,50 rather than 12.50. Read amounts using the person's number format, and show the interpreted value ("€12.50") so mistakes are obvious.
  • Label financial years clearly: "FY 2026–27" when a year spans two calendar years, "2026" when it doesn't.

Helpers you'll write

// The device's own date right now, as YYYY-MM-DD ("en-CA" formats dates this way)
function todayOnDevice(): string {
  return new Intl.DateTimeFormat("en-CA").format(new Date());
}

// A timestamp from another system, as a calendar date in a given time zone
function localDate(instant: Date, timeZone: string): string {
  return new Intl.DateTimeFormat("en-CA", { timeZone }).format(instant);
}

// Which financial year a date belongs to (returns the year it starts in)
function fyStartYear(dateISO: string, startMonth = 7, startDay = 1): number {
  const [year, month, day] = dateISO.split("-").map(Number);
  const onOrAfterStart =
    month > startMonth || (month === startMonth && day >= startDay);
  return onOrAfterStart ? year : year - 1;
}
// Australia (1 July):  "2026-06-30" → 2025   "2026-07-01" → 2026
// A 6 April start:     "2026-04-05" → 2025   "2026-04-06" → 2026
// US (1 January):      "2026-12-31" → 2026
Watch out
  • Store time zones as IANA names like Australia/Melbourne, never as offsets like +11:00. Offsets change with daylight saving.
  • Never add or subtract hours yourself to handle daylight saving. Let Intl and the IANA database do it.
  • Don't turn a date string into a JavaScript Date just to display it. new Date("2026-07-01") means midnight UTC, which shows as 30 June in the Americas. Keep dates as strings until the moment you format them.
  • Changing the time zone in Settings should not change any existing transaction dates. If dates are stored as dates, it won't.

Expense groups: keeping production separate from event costs

Every expense category belongs to exactly one group. This is what lets reports separate making things from selling them at an event or venue.

GroupExample categoriesLinked to an event or venue?
ProductionPrinting, merch manufacturing, art materials, packaging, shipping of stock to youNo. Stock usually serves many events and online sales.
Event & venueStall or table fees, vendor shelf rent, flights, accommodation, meals, local transport, display equipment hire, parkingYes. The app prompts for one, but allows "not assigned yet".
OperatingSoftware, website, equipment, marketing, payment fees, insurance, phoneNo
Why not spread production costs across events automatically? A print run might be sold at three markets and online over a year. Any automatic split, whether by revenue, by date or evenly, is a guess that will look precise but mislead. Keep production costs whole and visible. If artists ask for it later, add an optional "what did my stock cost for this event" estimate as a separate figure.

Rules baked into the design

  • Money is stored as whole minor units in integer columns: cents for dollars, pence for pounds. Not every currency has two decimal places (the yen has none, and a few currencies have three), so look up each currency's decimal places in ISO 4217 rather than assuming 2. A$110.00 is stored as 11000; ¥1,100 as 1100.
  • Dates are date columns, not timestamps (§6).
  • Every transaction stores both its original amount and its home-currency amount. Reports only ever add up home-currency amounts (§9).
  • Every transaction has a source (manual, receipt, csv, later square, stripe, email) and an optional external_id. A unique rule on account + source + external ID makes re-imports harmless (§14).
  • Categories come from a controlled list, not free text, so reports group cleanly.
  • Deleting an event doesn't delete its transactions. They become "no event".
  • Database changes are made through migrations, saved files that build the schema step by step and are committed to Git.

8. Sales tax setting (GST, VAT and sales tax)

Countries tax sales differently, so the setting is built from two simple questions instead of one country-specific switch:

  1. Do you charge tax on your sales? If yes, the tax portion of each sale belongs to the government, not the artist, so reports leave it out of income.
  2. Can you claim back the tax on your purchases? If yes, tax on receipts is tracked separately and reports show costs without it. If no, the tax is simply part of the cost.

Onboarding asks in the country's own words and fills in both answers:

Think about

  • Store a default rate per account, never a hard-coded 1/11. The tax inside a tax-inclusive price is total × rate ÷ (1 + rate), which gives 1/11 at 10%. Reduced and zero rates exist, so the rate is only a suggestion per entry.
  • Always record the tax shown on a receipt, even when it can't be claimed. It costs nothing to store, and the data is ready if the artist registers later.
  • People register partway through a year. Store a "registered from" date so reports treat each transaction according to its own date.
  • Not every purchase includes tax, and tax on an overseas receipt usually can't be claimed at home. Default foreign-currency receipts to "not claimable" and let the artist change it.
  • Use the country's word everywhere: GST, VAT or sales tax, in forms, reports and exports.
  • Check rates and rules for each country you market to. The app records; it never decides what's claimable.

9. Multiple currencies

An artist might take a commission from a US client, receive social-media income in US dollars or buy supplies from Japan. Each account has one home currency, and every report is in it. Foreign amounts are converted when they're entered, at the rate for the transaction or receipt date, and the result is locked.

What each transaction stores

FieldExample
Original currency and amountUSD 45.00
Home-currency amountAUD 64.29
Exchange rate used1.4286 AUD per USD
Rate date2026-10-22
Rate sourceYour rate provider, "Entered by artist" or "From Square"
How it was setAutomatic · artist entered the home amount · provided by the platform

For home-currency transactions, the original and home amounts are the same and the rate is 1.

The locking rules

  1. Use the rate for the transaction date, meaning the receipt or sale date, not the day it was typed in. A receipt from 3 March entered on 20 March uses 3 March's rate.
  2. No rate published that day? Weekends, public holidays and "today, before rates are out" all happen. Use the most recent earlier rate and show its date ("Rate from Friday 17 October").
  3. Once saved, the home amount is fixed. New rates never change old transactions, so last year's reports still match what was exported last year.
  4. Edits are explicit. Changing the foreign amount recalculates with the same locked rate. Changing the date asks "Use the rate for the new date?"
  5. The real amount beats a reference rate. If the artist knows exactly what left or arrived in their bank, including the bank's conversion margin, let them type the home amount. The app stores it and works out the rate. Nothing is more accurate.
  6. Platforms know their own rates. Square, Stripe, PayPal and similar services usually report the converted amount they actually paid out. When importing or integrating, use their figure rather than looking up a reference rate.

Getting exchange rates

  • Keep a shared fx_rates table: date, from currency, to currency, rate, source. A scheduled server job fills it daily and fetches older dates on demand for back-dated receipts. The browser can read it but never write to it.
  • Provider options: central banks publish free daily reference rates. The European Central Bank covers about 30 major currencies against the euro, and the Reserve Bank of Australia publishes AUD rates. Commercial rate services cover far more currencies and offer historical lookups, often with free tiers for small volumes. With artists in many countries, you'll need a provider that covers every currency you allow as a home currency.
  • Converting between two currencies the provider doesn't pair directly (e.g. NZD to JPY) goes through a common currency. That's fine as long as rates are stored with plenty of decimal places.

Getting the maths right

  • Store rates as exact decimals (Postgres numeric), never as JavaScript floating-point numbers.
  • Convert on the server or in the database, and round once, to the home currency's minor unit (§7).
  • Reports add up the stored home amounts. Never convert a total.
  • Convert tax and fees with the same rate as the amount they belong to.

Making it easy for the artist

  • The currency picker defaults to the home currency, or to the event's currency for an overseas event, so most entries never touch it. Recently used currencies appear first.
  • When a foreign currency is chosen, show the conversion live: "US$45.00 ≈ A$64.29 at 1.4286 (22 Oct)". It builds trust and catches typos.
  • On the receipt review screen, the AI reports the currency code it sees. A plain "$" is ambiguous, since Australia, New Zealand, Canada, the US and Singapore all use it. Default an unclear "$" to the home currency, and flag it when the supplier looks foreign.
Recommendation: lock the home currency once there are transactions If the home currency changed, every past home amount would still be in the old currency, and reports would mix the two. Let artists change it freely during onboarding and while the account is empty. After that, treat it as a support request, or as a deliberate "convert my history" tool built later.
Watch out Tax authorities may have views on which exchange rates are acceptable. Storing the rate, its date and its source with every transaction means any figure can be explained to an accountant. The app records the choice; it doesn't advise on it.

Subscription incomeMonthly memberships, e.g. Patreon or Ko-fiMonthly payouts with platform fees, often in a foreign currency. CSV import presets.
Decision: income counts when it's paid Income is recorded on the date the money is received ("cash basis"), so the app always matches the bank. A wholesale invoice sent on 20 June and paid on 15 July counts on 15 July, which is in the next Australian financial year. Each commission deposit counts when it arrives. Unpaid invoices aren't tracked in the first release. How income is reported for tax is still for the artist and their accountant to decide.

Designing cash-sale entry for a busy stall

  • A big "+ Sale" button on the home screen opens a number pad, not a long form.
  • Smart defaults: date = today on the device; event = whichever event or venue is on today, if any; payment = cash; stream = the event's usual stream; currency = the event's currency for an overseas event, otherwise home. Most sales then become: type amount, tap save.
  • Two styles, one table: some artists log every sale and others enter one total at the end of the day. Both are simply income rows, so support both without special code.
  • A running total for the event on screen gives instant feedback ("Today: $640 from 23 sales").
  • Easy undo and edit, because fat-finger errors happen when a queue is waiting.
  • Helper-friendly: this is the screen a future helper with only transactions.add would use (§5), so keep it fully usable without access to reports.

Card and online sales

  • Record the gross sale amount and any fees separately, so fees show up as a cost instead of quietly shrinking revenue.
  • Refunds are their own rows with a negative amount, linked to the original sale. Never edit the original sale's amount.
  • Payouts aren't income. When Square or Stripe deposits money into the bank, that's a transfer of sales already recorded. Counting it again would double the income. Vendor shelf payouts are the exception: the store's payout is how those sales get recorded, because the artist has no other record of them.

11. Receipts and original images

Getting the file: camera, photo library and PDFs

<input type="file" accept="image/*,application/pdf" multiple />

Leave out the capture attribute. With capture, phones jump straight to the camera. Without it, iPhones and Android phones offer a menu: take a photo, choose from the photo library, or pick a file. multiple allows a batch of receipts at once.

The best way to keep the original

  1. Upload the file exactly as received. Don't resize, compress or convert the stored original. Tax authorities such as the ATO accept digital copies only if they're a true and clear reproduction, and you never know which detail matters later.
  2. Make a separate preview, a smaller JPEG, for fast display and for sending to the AI. It can be made in the browser before upload or on the server. HEIC photos from iPhones are a good example: store the HEIC as-is, and make a JPEG preview because most non-Apple browsers can't show HEIC.
  3. Use a private bucket and a predictable path such as receipts/{account_id}/{receipt_id}/original.heic. Storage policies check that the first folder is an account the logged-in user belongs to, using the same permission function as the tables (§5).
  4. Never overwrite. Upload with overwrite turned off. "Replace photo" creates a new receipt record, and the old one is soft-deleted.
  5. Record a fingerprint. Save a SHA-256 hash of the file. If the same file is uploaded again, warn "You've already uploaded this receipt".
  6. Make deletion deliberate. Set deleted_at first and remove the file after a grace period. Remind the user that tax records must be kept for years: 5 in Australia, with other countries setting their own periods.
  7. Keep a second copy elsewhere. Supabase's database backups don't include files in Storage. Before launch, set up a scheduled job that copies new receipts to a separate storage provider with versioning turned on.
Privacy detail Phone photos often contain hidden location data (EXIF GPS). Keep the original intact, since it's the record, but strip metadata from previews, and never make originals publicly reachable. Show them only through short-lived signed links.

Reading the receipt automatically

Use one vision-capable AI model call per receipt. It returns draft fields and a suggested category from your fixed list, all in a structured format. A separate categorisation service isn't needed.

  1. The file is uploaded and a receipts row is created with status uploaded.
  2. A server route sends the preview to the AI. It asks for supplier, date, currency code, total, tax, the supplier's tax or business number if present, a line-item summary and a category chosen only from your list.
  3. Your code checks the result: is the date a real date, do the amounts parse, is the tax not greater than the total, is the currency a real currency code, is the category on the list?
  4. The artist sees a pre-filled form next to the photo, corrects anything wrong, confirms the currency, picks an event or venue if relevant and saves. Foreign amounts are converted and locked at that moment (§9).
  5. Nothing becomes an expense until the artist taps save.
  • Always allow manual entry. If the AI is slow, down or wrong, the artist can still type it in.
  • Measure before you scale. Track how often each field gets corrected and the cost per receipt. Collect 30–50 real, anonymised receipts as a test set and re-run it when you change models or prompts.
  • Check data terms for whichever AI provider you choose: retention, whether data is used for training, and where it's processed. Mention the provider in your privacy policy.

12. Reports and exports

The main profit view

Filterable by financial year (or a custom date range), event or venue, and income stream. All amounts are in the home currency (§9). If the artist charges and claims back tax, amounts exclude it (§8).

Income $12,400 less Selling fees (card/platform) −$310 Net sales $12,090 less Production costs −$3,850 Gross profit $8,240 less Event & venue costs −$2,100 less Operating costs −$1,450 Net profit $4,690

Other views

  • By event or venue: income minus that event's or venue's event & venue costs = its result. For vendor shelves, this shows whether the rent is covered. Add a clear note that production costs aren't included (§7).
  • By income stream: income per stream, so the artist sees whether commissions or markets carry the business.
  • By month: a simple chart of income vs costs, to show seasonal patterns.
  • Needs attention: event & venue costs with no event, foreign amounts still waiting for a rate, receipts awaiting review, imports with skipped rows.

Do the maths in the database

Calculate totals with SQL (views or database functions), not by downloading every row and adding them up in the browser. It's faster, and the export and the screen use the same numbers.

Exports

  • Transactions CSV: every income and expense row for a chosen period, with event, stream, category, group, tax and source, plus the original currency and amount, the home-currency amount, and the rate, rate date and rate source.
  • FY summary: the profit view above for one financial year, plus totals by category, event and stream. Start with CSV, and add a nicely formatted version later if artists ask.
CSV export gotchas
  • Write amounts in the currency's normal form (110.00, or 1100 for yen), not minor units. Your accountant shouldn't have to divide by 100.
  • Separators differ by country. In some countries Excel expects semicolons between columns and commas as decimal marks. Offer two choices: "Standard CSV" and "Excel (semicolon)".
  • Write dates as 2026-07-01, which no spreadsheet misreads as American month/day.
  • Add a UTF-8 "byte order mark" at the start of the file so Excel shows accented names and symbols correctly.
  • Formula injection: a supplier name starting with =, +, - or @ can run as a formula when opened in Excel. Prefix such text cells with an apostrophe. Don't do this to number columns, or negative amounts would break.

13. CSV import

Most selling platforms (Square, Stripe, Etsy, Shopify, PayPal, Patreon, Big Cartel) let artists download sales as CSV. A good import screen gives artists most of the value of direct integrations long before you build them. It's also a rehearsal for building those integrations.

The import pipeline

  1. Upload: the file goes to the server. Set a size limit and accept only .csv.
  2. Parse: use a proper CSV library. Never split lines on commas yourself, because quoted fields contain commas.
  3. Map columns: the artist matches their columns to yours (date, amount, fees, description, ID…). Offer saved presets per source, such as "Square sales export", so next time it's one tap.
  4. Stage and validate: load rows into a temporary staging area, never straight into income. Check every row and mark problems.
  5. Preview: show the result ("142 sales, $8,320 total, 3 rows need attention, 12 already imported") before anything is saved.
  6. Commit: save valid rows in one go, all tagged with the import_batch ID.
  7. Undo: "Remove this import" deletes every row from that batch. This is a huge confidence-builder for users.

Structure considerations

ProblemHow to handle it
Ambiguous dates (is 03/04/2026 3 April or 4 March?)Ask the user to confirm the format in the mapping step. Auto-detect only when a day value over 12 makes it certain.
Dates with times and time zonesConvert to the account's time zone, or the event's if it was held elsewhere, then keep only the calendar date (§6).
Amount formatsStrip currency symbols and thousands separators, respecting the file's decimal mark (1.234,50 vs 1,234.50; ask when unclear). Treat (12.50) as negative. Convert to minor units only after validating.
CurrenciesMap a currency column if there is one; otherwise ask which currency the file is in. If the file includes the platform's own converted amount, use it as the home amount. Otherwise convert each row at its own date's rate (§9).
Gross vs fees vs netMap gross and fees separately. If only net is available, import net and flag that fees are missing.
RefundsImport as negative income, linked to the original sale where the export gives its ID.
Payouts and transfersSkip them. They aren't sales (§10).
DuplicatesUse the platform's transaction ID as external_id. If there's no ID, build a fingerprint from date + amount + description and warn about likely duplicates.
Assigning eventsSuggest an event or venue when a sale's date falls within its dates. The artist confirms in the preview.
Assigning income streamsDefault stream per import preset (e.g. Etsy → online sales, Patreon → subscription income), changeable per row.
Partial failuresNever import silently with gaps. Show which rows were skipped and why, and let the artist fix or skip them.
Customer detailsSkip customer names, emails and addresses by default. Reports don't need them, and data you don't store can't leak (§16). Keep only the order or transaction ID.
TraceabilityKeep the original row data with each imported record so you can explain any figure later.

The same pipeline can import expenses later, such as a bank statement export, with the same safety features.

14. Ready for Stripe and Square, without building them yet

You don't need to write any integration code now. You only need to avoid decisions that would block it later. The design above already does this:

  • source and external_id on every transaction, with a unique rule, so re-syncing never duplicates.
  • Gross, fees and refunds stored separately, matching how payment platforms report sales.
  • Original and home-currency amounts with a recorded rate source, so a platform's own conversion can be stored as is.
  • Account-based ownership, so a connection belongs to the business, not to whichever person connected it.
  • Time-zone conversion helpers already written for CSV import.
  • Important logic in server route handlers that external services can call (§4).
  • The CSV import pipeline (stage → validate → commit by batch), which integrations can reuse.

What the integrations will involve later

  • Square: the artist approves access through Square's OAuth screen with read-only permissions. Your server then fetches payments and listens for webhooks.
  • Stripe: reading another business's existing Stripe account is more restricted. Stripe's read-only access is limited to apps registered as Stripe Extensions or Apps. Expect a separate registration and review process, which is a good reason to do Square first.
  • Countries: Square and Stripe operate in different sets of countries. Check where your artists are before choosing which to build first.
  • Both: an integrations table for encrypted tokens and sync progress, a "Disconnect" button, webhook signature checks and sync jobs that are safe to retry.

15. The installable app (PWA)

A Progressive Web App is a website that can be installed with an icon and opens full-screen like an app. One codebase serves iPhone, Android and desktop.

What's involved

  • A web app manifest: name, icons, colours and "standalone" display.
  • A service worker: a small script that can cache the app's own files so it loads fast. Use Next.js's PWA guide or a maintained library, and cache only the app's own static files at first. Don't cache financial data.
  • An update strategy so a new deployment doesn't leave users stuck on an old, broken version.

iPhone specifics

  • iPhones never show an automatic "Install app" prompt. Show your own short instructions: Share → Add to Home Screen.
  • The installed app has separate storage from Safari, which is why login uses codes (§5). A user who installs the app logs in once more inside it.
  • Test the camera and photo-library input inside the installed app, not just in Safari.

Offline, scoped small

Market halls often have poor signal. Full offline sync is complex, but a narrow version is very achievable: save receipt photos and cash sales on the phone, then upload when back online. Store pending items in the browser's IndexedDB, give each a unique ID so a retry can't create duplicates, and delete them only after the server confirms. Safari doesn't support background sync, so retry when the app is opened. Show clearly what's still waiting to upload. This is an optional stage (Stage 10); decide after talking to artists.

Mostly documents and habits rather than code. The build additions are small: policy-version and marketing-consent fields, a complete account-deletion purge, imports that drop customer details by default, and a log of any admin access to user data. A small exercise: turning typed amounts into cents

const amountPattern = /^\d+(\.\d{1,2})?$/;   // "110", "110.5", "110.50"

function toCents(input: string): number | null {
  const clean = input.trim();
  if (!amountPattern.test(clean)) return null;
  const [whole, fraction = ""] = clean.split(".");
  return Number(whole) * 100 + Number((fraction + "00").slice(0, 2));
}
// toCents("110.5") → 11050

Try extending it: what should happen with $110, 1,100.00 or 0? Decide, then write the rule.

This version assumes two decimal places and a full stop as the decimal mark. In Stage 4 you'll generalise it: the number of decimal places comes from the currency (§7) and the decimal mark from the person's number format (§6).

  1. Create a private receipts bucket with account-folder policies that use the permission function.
  2. Add the file input (camera, library and PDF; multiple files).
  3. Upload originals untouched, create previews, and save the receipts row with hash and metadata.
  4. Attach a receipt to an expense, entered manually for now, and view it through a signed link.
  5. Add duplicate-file warnings and soft delete.

Watch out

Test uploads from an iPhone's photo library (HEIC) and camera, and from a PDF, inside the installed app.

Check yourselfCould another user open one of your receipts if they guessed its path? Why not?

Done when: receipts upload from camera, library and files, originals are unchanged byte for byte, and only account members with permission can view them.

Stage 8

Reading receipts automatically

Read first: §11

You'll learn

Calling an AI API from the server, structured outputs, validating untrusted data and designing a review screen.

Steps

  1. Collect 30–50 real receipts (anonymised) with the correct answers written down.
  2. Write a server route that sends a preview to the AI and asks for structured fields plus a category from your list.
  3. Validate the response, then show the side-by-side review form.
  4. Track extraction status, errors and which fields users corrected.
  5. Run your test set, note accuracy and cost per receipt, and adjust.

Watch out

Keep the AI key on the server only. Add a per-user daily limit so a bug or abuse can't run up a large bill.

Check yourselfWhat happens if the AI service is down when an artist uploads a receipt?

Done when: most receipts need little or no correction, failures fall back to manual entry, and nothing is saved without the artist confirming.

Stage 9

CSV import

Read first: §13

You'll learn

Parsing files, data cleaning, staging tables, transactions (all-or-nothing saves) and idempotency.

Steps

  1. Download real sales exports from Square, Etsy, Stripe, Shopify or Patreon test accounts to practise on, including one in a foreign currency.
  2. Build upload → parse → column mapping (with saved presets) → staged preview → commit → undo.
  3. Handle dates, amounts, currencies, refunds, payouts and duplicates as described in §13.
  4. Import the same file twice. The second import should add nothing.
Check yourselfHow does the app know a row was already imported when the file has no transaction IDs?

Done when: a real export imports correctly, re-importing creates no duplicates, and any import can be undone.

Stage 10 · Optional

Offline queue for market days

Read first: §15

Build this only if artists say signal at markets is a real problem. Queue receipt photos and cash sales on the phone with unique IDs, upload when back online, retry when the app opens, and show what's pending. Test in airplane mode, after closing the app and with a half-finished upload.

Done when: sales and photos captured offline appear exactly once after reconnecting.

Stage 11

Getting ready for real users

Steps

  1. Move hosting to paid plans before charging anyone (§18). Keep a separate free Supabase project for development.
  2. Set up custom SMTP so login codes reach anyone, and send a test to Gmail, Outlook and iCloud addresses.
  3. Set up the scheduled off-site copy of receipt files, and practise restoring both the database and a receipt.
  4. Add error monitoring that doesn't record receipt contents or amounts.
  5. Work through §16: data map, privacy policy and terms (with a data processing agreement), provider agreements, breach response plan and a Singapore data protection officer. Confirm the sign-up country list excludes the EU and UK. Then have a privacy lawyer review it all.
  6. Check the tax wording, default rates and financial-year defaults for each country you'll market to.
  7. Confirm your exchange-rate provider covers every home currency you allow, and that its terms permit commercial use.
  8. Arrange a security review of RLS, storage policies and route handlers.
  9. Run the full testing checklist with a few friendly artists.

Done when: you can recover from a failure, explain how data is protected, and new users can sign up without your help.

Stage 12 · After launch

Forward-to-email receipt inbox

Each artist gets a private address (e.g. receipts+k7f2q@yourdomain). An inbound-email service receives the message and calls one of your route handlers, which checks the sender is a verified address for that artist. Attachments then go through the same receipt pipeline as uploads, into the review queue. Plan for spam, size limits and invoices sent as links rather than attachments.

Stage 13 · When artists ask

Square, then Stripe

Follow §14. Start with Square (read-only OAuth), reuse the import pipeline and external_id rules, verify webhooks, and add Disconnect. Approach Stripe once you've confirmed the Extension or App registration path.

Will storage get expensive?

Suppose an active artist uploads 300 receipts a year at about 3 MB each. That's roughly 1 GB per artist per year, so Supabase Pro's 100 GB covers around 100 artist-years of originals. After that, extra storage costs cents per GB. Storage is unlikely to be your biggest cost; AI processing and your own support time probably will be.

Pricing your app Before choosing a subscription price, estimate cost per artist per month: hosting share, AI cost per receipt × receipts per month, storage, email, payment-processing fees on your own subscriptions, and support time. Re-check after your first 20 real users.

19. Testing checklist

Money and dates

  • Transactions on 30 June and 1 July land in the correct financial years.
  • A calendar-year account (e.g. US or Singapore) and a mid-month start (e.g. 6 April) put boundary dates in the right years.
  • Dates display in each person's local format but are stored as YYYY-MM-DD.
  • A late-night entry in Perth and an early-morning entry in Sydney get the right local date.
  • Changing the time zone in Settings doesn't change existing dates.
  • Reports are correct under each tax setting, against hand-checked test data.
  • Refunds reduce income, payouts are never counted as income, and fees appear as costs.
  • Event results exclude production costs and say so.

Currencies

  • A weekend-dated foreign receipt uses the previous published rate and shows which date it came from.
  • Saved home amounts don't change when new rates arrive.
  • An artist-entered home amount is kept exactly, with the rate worked out from it.
  • Yen (no decimals) and a three-decimal currency store and display correctly.
  • 12,50 typed with a European number format is read as 12.50.
  • Report and export totals match hand-checked home-currency totals.

Privacy and security

  • Two-account test passes for every table, every route handler and every stored file.
  • A test helper with only "add sales" can add sales, but can't see reports, other entries or settings, or change their own permissions.
  • Removing a member cuts off their access immediately.
  • No secret keys in browser code, Git history or logs.
  • Login works inside the installed iPhone app using the emailed code.
  • Database and receipt-backup restores have been practised.

Privacy

  • Deleting an account removes its data and files within the stated period, apart from backups that expire on schedule.
  • A user's exports contain all the personal data the app holds about them.
  • The accepted policy version, and marketing opt-in, are recorded for every user.
  • CSV imports drop customer names, emails and addresses unless the artist deliberately maps them.
  • The breach response plan has been rehearsed once.

Receipts and imports

  • Camera, photo library (including HEIC) and PDF all work on iPhone and Android, inside the installed app.
  • Stored originals are byte-for-byte identical to what was uploaded.
  • Nothing from the AI is saved without the artist confirming. Manual entry works when the AI fails.
  • Importing the same CSV twice adds nothing. Undoing an import removes exactly that batch.
  • Exported CSVs open correctly in Excel and Google Sheets, and text starting with = doesn't run as a formula.

Everyday use

  • A cash sale can be logged in a few seconds with one hand.
  • Buttons are large enough to tap, text is readable outdoors, and the app works with a screen reader and keyboard.
  • New deployments reach installed apps without reinstalling.

20. Glossary

Account and account member
An account is an artist's business and its records. A member is a person allowed into it, with a role and permissions.
Browser vs server code
Browser code runs on the user's device and can be inspected by anyone. Server code runs on your hosting and can safely hold secrets.
Calendar date vs timestamp
"1 July 2026" vs an exact instant like 1 July 2026 09:00 in Melbourne. Receipts and sales are recorded as calendar dates.
Controller and processor
The controller decides why and how personal data is used. A processor handles it on the controller's behalf. You're the controller for your users' details, and a processor for the customer details inside artists' records.
CRUD
Create, read, update, delete: the four basic things you do with records.
Data processing agreement (DPA)
A contract setting out how a processor may handle personal data for a controller. You accept one from each provider and offer one to your users.
Environment variables
Settings and keys stored outside your code, e.g. in .env.local locally or in hosting settings.
Home currency
The currency an account reports in. Every foreign amount is converted into it.
IANA time zone
A standard name like Australia/Melbourne that knows that region's daylight-saving rules.
Idempotent
Safe to repeat. Running an import or sync twice gives the same result as running it once.
Locked rate
The exchange rate saved with a transaction when it's entered. Later rate changes never alter it.
Migration
A saved, versioned file describing a change to your database structure.
Minor units
A currency's smallest unit, such as cents or pence. Money is stored as whole minor units to avoid rounding errors.
OAuth
The "Allow this app to access your account" approval flow used by Square, Stripe and Google.
OTP
One-time passcode: the 6-digit code emailed to the user at login.
PWA
Progressive Web App: a website that can be installed and behaves like an app.
Route handler
A server-side web address in your Next.js app that receives a request and returns a response.
RLS (Row Level Security)
Database rules that decide which rows each logged-in user can see or change.
Security definer function
A database function that runs with its creator's rights. Used carefully, it lets RLS policies check membership safely.
Service worker
A background script that can cache app files and make the app load quickly or partly offline.
Signed URL
A link to a private file that works for a short time only.
Staging table
A holding area where imported rows are checked before they become real records.
Webhook
A message another service sends to your server when something happens, e.g. a new Square payment.
